# Changelog

All notable changes to Vigil will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added

- **Release mechanism for the `v1` major alias, plus a drift detector** — Every consumer repo pins the action at `F2iLLC/vigil@v1`, but nothing repointed that alias on merge, so **merging to `main` shipped nothing**. The gap recurred four times, twice within hours of a merge, and was each time found by a human comparing SHAs by hand. It has a demonstrated cost: `766362c` (*review documentation PRs instead of auto-approving them*, #62/#63) sat merged-but-unshipped while `vigil-reviewer` approved F2iLLC/LunaOS#4223 and #4224 with *"Documentation-only changes detected; Vigil auto-approved without model review"* — the exact rubber-stamping that commit removes. Two new workflows now cover this, kept separate on purpose. `Tag drift check` (`.github/workflows/tag-drift-check.yml`) is **report-only**: on push to `main`, daily, or on demand, it fails loudly when `v1` lags `main` or when an in-repo `F2iLLC/vigil@<sha>` self-pin is stale — the second surface matters because those pins do not follow the alias, so releasing `v1` never refreshes them. It never touches a tag. `Release (move major alias tag)` (`.github/workflows/release.yml`) performs the move, triggered by pushing a `vX.Y.Z` semver tag (the alias is derived from the tag's major component) or by a dry-run-by-default `workflow_dispatch`, and gated on the `release` environment. It **deliberately does not trigger on push to `main`**: this repo's own review workflow is `disabled_manually`, so PRs here land with zero checks and zero review, and auto-shipping every merge from an unreviewed branch to five consumer repos — one of them the reviewer gating all the others — trades a visible staleness problem for an invisible blast-radius one. Tying the alias to a semver tag also closes a gap nothing else covers: there is currently no numbered tag anyone can pin to for the commits on `main`, and `v1` already sits ahead of `v1.1.0`. The release refuses to proceed unless the full test suite passes (issue #58's own first constraint — both manual retags were gated on a local `pytest`), `action.yml` inputs remain consumer-compatible (its second constraint), the target is contained in `main`, and the alias is not moving backwards. Supporting tooling: `.github/scripts/tagctl.sh` (`resolve`/`drift`/`pins`/`plan-move`/`move` — local tags only, it never pushes) and `.github/scripts/check_action_inputs.py`, both covered by `tests/test_release_tooling.py`. `tagctl.sh` exists largely to hold **one** correct implementation of a single detail: `v1` is an *annotated* tag, so `git rev-parse v1` yields the tag object (`4a2f385…`) rather than the commit (`67379a5…`), and a checker that skips the `^{commit}` peel reports permanent phantom drift. That mistake has already misled an automated run of this repo. Addresses F2iLLC/vigil#58; **the release-trigger policy itself remains an owner decision.**
- **Pluggable external context provider** — Vigil could only review a PR against the PR itself, so a claim falsifiable only against material *outside* it (a completion report asserting a milestone is done while the code is an empty stub) had no evidence base and could not be challenged. A single optional provider can now be configured — `VIGIL_CONTEXT_PROVIDER` / the `context-provider` action input — as either a command (argv-parsed, run without a shell) or an `http(s)` endpoint. It is invoked once per review with the PR coordinates (`repo`, `pr_number`, `head_sha`, `changed_paths`), returns opaque text plus an optional short label, and that text is injected by `_build_pr_context_block()` alongside the conversation section so it reaches every specialist and the lead from one place. Vigil stays entirely agnostic about what the context *is*: it never parses, models, validates, or writes back to the source, carries no knowledge of any specific external system, and holds at most one opaque operator-supplied token (`VIGIL_CONTEXT_TOKEN`, forwarded as an env var or an `X-Vigil-Context-Token` header). The block frames the payload as untrusted evidence that may be machine-generated and explicitly **not** instructions — an injected directive arriving this way is deliberately *not* promoted to a finding, because that would let a hostile provider manufacture findings on an unrelated PR. Payloads over `VIGIL_CONTEXT_MAX_CHARS` are truncated deterministically (first N characters) with the truncation stated in the block, never silently. The seam fails open on every path — unconfigured, empty output, non-zero exit, non-2xx status, timeout (`VIGIL_CONTEXT_TIMEOUT`, default 20s), or unparseable command — and can never block or fail a review. Fork safety is enforced in `.github/workflows/reusable-vigil.yml`, not just documented: a new fork-gate step resolves `context-provider`, `context-label`, and `context-token` to empty unless the event is `pull_request` **and** the head repository equals the base repository, so everything it cannot positively prove (including on-demand `/vigil review`, whose `issue_comment` payload carries no head-repository provenance) fails closed. Implements F2iLLC/vigil#47.
- **Loud-failure guard in the composite action** — `action.yml` now has a final `Verify Vigil actually ran` step that runs with `if: always()`, so it still executes even when an earlier step (e.g. `Install Vigil into a venv`) failed and left `Run Vigil` skipped. When either step did not succeed, the guard fails itself, emits an `::error::` workflow annotation, and appends the same statement to `$GITHUB_STEP_SUMMARY` — for every command (`review`, `dismiss-resolved`, `resolve-addressed`). Only the `review` command additionally gets a best-effort PR comment via a plain `curl` call to the GitHub REST API (the venv Vigil is normally installed into may not exist, so the guard cannot shell out to the `vigil` package itself): posted only when a PR number is resolvable, and skipped when a prior comment on the same PR already carries a `<!-- vigil-did-not-run -->` marker (one best-effort, unpaginated lookup — a failed or unrecognized lookup falls through to posting rather than going silent). `dismiss-resolved` and `resolve-addressed` never get the comment: neither posts a review in any outcome, so neither creates the false attestation this guard exists to catch, and `resolve-addressed` in particular fires on every `synchronize` event — commenting there too would spam every open PR on every push for as long as an outage lasts. The action also gains a new `review-ran` output (`true`/`false`) so a caller can gate on an actual completed review explicitly. None of this changes the reusable workflow's `advisory` default (still `true`): a Vigil job that could not run stays non-blocking for merge gating by default, but is now unmissable in the run itself instead of silently reporting green. Addresses item 1 ("fail loudly") of F2iLLC/vigil#51; the `advisory` input in `reusable-vigil.yml` now documents this tradeoff inline, and the README gained an "Advisory mode and loud failure" section. Root incident: F2iLLC/relara run 30927732554, fleet-wide via F2iLLC/LunaOS#3775.
- **PR conversation context** — Specialists and the lead reviewer now receive the PR's conversation thread (issue comments, bot replies, prior review bodies) alongside the diff, not just the diff itself. A shared "FACTUAL CLAIMS VS. THREAD EVIDENCE" instruction (specialists) and scope-check bullet (lead) direct reviewers to flag a `factual-accuracy` finding when the diff/description asserts something the thread already contradicts — e.g. a doc change claiming "X was never connected" when a bot reply in the same thread says otherwise. Fixes the class of failure in #2698 (LunaOS) where a diff-only review approved a PR whose central factual claim was contradicted in its own comment thread.
- **Webhook server** — `vigil serve` starts a FastAPI server that receives GitHub webhook events and triggers reviews automatically. No more GitHub Actions minutes burned. Configure with `WEBHOOK_SECRET` for signature verification.
- **Non-blocking specialists** — Personas can be marked `blocking=False` (Security is non-blocking by default during early dev). Their findings become observations and don't block the review decision.
- **Email alerts** — Personas with `alert=True` trigger email notifications for their findings. Security findings send alerts even though they're non-blocking. Configure with `VIGIL_ALERT_EMAIL` and SMTP env vars.
- **Smart resolution verification** — When someone replies to a Vigil comment with an issue link (`#45` or full URL), Vigil fetches the issue and verifies it actually covers the concern (keyword overlap check). Prevents agents from dismissing findings by linking unrelated issues.
- **Expanded resolution keywords** — Resolution replies now accept "resolved", "fixed", "addressed", "done", issue links (`#123`), and combinations ("Fixed in #45").
- **Dedup against resolved threads** — New `fetch_all_vigil_comments()` includes comments from resolved threads in dedup checks. Prevents Vigil from reposting the same findings when threads are resolved by users or agents without fixing the underlying code.
- **Incremental review** — On re-review, Vigil only analyzes files changed since the last review commit, reducing noise and cost.
- **Auto-resolve addressed threads** — When re-reviewing, Vigil resolves its own comment threads where the underlying code has changed.
- **Dismiss-resolved command** — `vigil dismiss-resolved <pr-url>` resolves Vigil threads that received a "resolved" reply.
- **Force inline comments** — On a blocking verdict, findings are placed as inline diff comments. Findings on non-diff lines are relocated to the nearest commentable line with a note. Findings on files not in the diff are attached to the best-matching file. (Narrowed to blocking verdicts only — see "Inline comments only on a blocking verdict" under Fixed.)
- **Comment deduplication** — New comments are compared against existing Vigil comments using path-indexed lookup, MD5 fingerprint fast-path, and `SequenceMatcher` fuzzy matching (0.85 threshold).
- **Batched GraphQL mutations** — Thread resolution uses batched mutations (up to 50 per request) instead of N+1 individual calls.
- **`/vigil review` command** — Re-trigger a review by commenting `/vigil review` on a PR (works with both webhook and GitHub Actions).
- **Test suite** — 167 tests covering diff parsing, comment management, HTTP errors, webhook events, alerts, and resolution verification.

### Changed

- **Security reviewer non-blocking** — Security specialist findings are treated as observations (non-blocking) by default. Configurable via `blocking` flag on `Persona`. Set `blocking=True` to make security blocking again for production.
- **GitHub Actions workflow** — Removed `synchronize` trigger to stop per-commit reviews. Added `issue_comment` trigger for `/vigil review` command. Workflow is now opt-in and can be disabled independently of the webhook server.
- **Thread matching** — Uses `(path, line, session_id)` tuples instead of brittle `body[:100]` for matching REST comments to GraphQL threads.

### Fixed

- **A review in which no specialist ran is no longer an approval** — A PR whose diff touched only shell or script files matched **no** persona's `file_patterns`, so all seven specialists were skipped as `NOT REVIEWED — no files in scope` and the aggregate verdict came back `APPROVE` at 0/7. At the API level that approval was indistinguishable from a real one (`vigil-reviewer:APPROVED`, `reviewDecision=APPROVED`, `reviewCount=1`), so it satisfied the org ruleset's required-approval rule and the PR merged with **zero review**. Observed on F2iLLC/LunaOS#5028, whose entire diff was `scripts/heartbeat-ping.sh`. Two independent halves are fixed, and the categorical one is the load-bearing half. **(A) Categorical.** `review_diff()` now downgrades the aggregate verdict to a new `DECISION_NOT_REVIEWED` (`"NOT_REVIEWED"`, defined in `models.py`) whenever a profile has specialists and **none** of them ran. It maps explicitly to a GitHub `COMMENT` event, which is precisely the semantics wanted: the review still posts and still says everything it has to say, but it counts toward no approval requirement — and it does not block either, because nothing was examined, so there is nothing to object to, and failing closed on every diff no persona happens to scope would stall the fleet in the opposite direction. This half holds for **any** file type nobody scoped, including extensions nobody has thought of yet, so the fix does not depend on the list in (B) staying complete. Two boundaries are pinned by their own tests: a **blocking lead verdict is never downgraded** (the lead reads the full diff and can object even when no specialist ran, so rewriting its `REQUEST_CHANGES` into a non-blocking `NOT_REVIEWED` would be this same fail-open pointed the other way), and a **partial** skip is untouched — any specialist having run leaves the verdict exactly as #66 settled it, which is why every one of #66's gating tests still passes unmodified. The one behavioral change beyond the reported symptom is deliberate and called out here: when *every* specialist is unavailable through transient provider errors, the verdict is now `NOT_REVIEWED` rather than `APPROVE` (`tests/test_reviewer.py::test_503_does_not_block_overall_review`, whose stated invariant — a provider outage must never become a merge block — is unchanged and still asserted). Approving through an outage is the same fail-open with a different cause. **(B) Instance.** No persona scoped scripts at all: `.sh`, `.bash`, `.zsh`, `.fish`, `.ps1`, `.psm1`, `.bat`, `.cmd`, `.mjs` and `.cjs` appeared **zero** times in `personas.py`. Two named groups, `SCRIPT_PATTERNS` and `JS_PATTERNS`, now carry them, spliced into the correctness and security personas of both profiles (`Logic`/`Security` in `default`, `Architecture`/`Security` in `enterprise`) and, for the JavaScript group, into **every** persona that already scoped `*.js` — named groups rather than repeated literals precisely because eight hand-maintained copies with a silent hole in each is how the gap arose. `.mjs`/`.cjs` are ordinary Node JavaScript and were unreviewable by accident: `*.js` does not glob-match `foo.mjs`, and LunaOS ships `scripts/setup-git-hooks.mjs`, which wires `core.hooksPath` and can disable every git hook in a clone. Scripts are where the dangerous code disproportionately lives — deploy steps, credential handling, `rm -rf`, `curl | sh`, hook installation; `.github/workflows/*.yml` was already covered by `*.yml`, but a standalone `.sh` invoked *from* a workflow was not. `Security` had been masking the hole by accident, since its substring globs (`*auth*`, `*secret*`, `*token*`, `*crypto*`, `*middleware*`) caught `deploy-token.sh` while `deploy.sh` matched nothing — a script's coverage depended on whether its filename happened to contain one of five words. `TS_PATTERNS` does the same for `*.mts`/`*.cts`, found while reviewing this change — `*.ts` no more glob-matches `foo.mts` than `*.js` matches `foo.mjs`, and in a TypeScript monorepo that is the likelier of the two holes. **The cost of (A) is stated here rather than left to be discovered:** because `NOT_REVIEWED` grants no approval, and in these repos Vigil's approval is the one the ruleset requires, every PR shape that still reaches no specialist now needs a **human** approval — and unlike a `REQUEST_CHANGES` that is deterministic, since re-running Vigil yields the same verdict forever. Verified against both real profiles, that set is: `.css`/`.scss` (deliberately excluded from every persona), `Dockerfile`, `Makefile`, extensionless scripts (`scripts/deploy`), `.tf`/`.hcl`, `.gitignore`, `CODEOWNERS`, `LICENSE`, `.vue`, `.html`, `.c`, `.kt` and `.csv`. That is a fair trade against silently merging them unreviewed, but it is wider than the shell case this issue reported, so it is pinned by `TestKnownCoverageGapsAreDeliberate` — the list is asserted, so changing it is a visible diff rather than an accident, which is precisely what #79 lacked. **Whether to close that gap by broadening the persona patterns or by adding a catch-all specialist (making `NOT_REVIEWED` a genuine last resort) is an owner decision and is deliberately not settled here.** **(C) Reporting.** When no specialist ran, the lead's prose summary is now preceded by an explicit caveat and the header renders `⏭️` instead of `✅`. The lead *does* receive the full diff, so that summary is not invented — but it is written to read as a synthesis of specialist verdicts that in this case do not exist, and on #5028 it produced a fluent paragraph (*"well-scoped, follow existing project idioms"*) that a human skimming the review had no way to discount. The caveat sits above the summary rather than deleting it: a reader who wants the lead's read can still have it, they just cannot mistake it for a review. **Documentation-only PRs are unaffected**, and structurally rather than by special case: the `DX` persona scopes `*.md` in both profiles, so a documentation diff always has a live specialist and never reaches the all-skipped branch — pinned by `TestDocumentationOnlyPathIsUnaffected` because those PRs are how the heartbeat lands its own state, and a fix to the review gate that stalls the fleet a different way is not a fix. (The documentation-only *auto-approve short-circuit* older supervisor guidance still describes no longer exists here; #62/#63 removed it, and `is_documentation_only` survives as a classifier with no production caller.) `BLOCKING_DECISIONS` moved from `github_review.py` to `models.py` so the review engine and the posting layer read one definition; it is re-exported from its old home, so existing imports are unchanged. Fixes F2iLLC/vigil#79. **Consumers pin `F2iLLC/vigil@v1`, so this reaches zero repos until the `v1` alias is moved — a fleet-wide release that remains an owner action.**
- **Findings are checked against the commit they cite before they are posted** — Every finding is stamped with `head_sha` (`reviewer.py`) and written to GitHub as the review's `commit_id` (`github_review.py`), and **nothing validated that the cited file or code exists at that commit** — Vigil never fetched file content at any point, from any endpoint. On F2iLLC/LunaOS#4528 that produced seven CRITICAL *"Cannot find namespace JSX"* findings across three pushes, each stamped with that push's correct post-rebase head, against `AdminUserList.tsx` and `ThemeShowcase.tsx` — both of which already carried `import type { JSX } from "react"` at every one of those commits, with repo-wide CI typecheck green throughout. The findings described pre-rebase content while citing a correct-looking post-rebase SHA, which is the worst available combination: the SHA is exactly what makes the claim look verified. Three seams are closed. **(A)** A new `finding_validation.validate_findings_against_head()`, called from `post_review` between the cross-round filter and the routing step, fetches each cited file at the exact reviewed commit (`github.get_file_content_at_commit`, raw media type, cached per `(path, sha)` so a dozen findings in one file cost one blob) and withholds a finding on **positive evidence only**, in exactly two shapes. **Absence** requires all three of: the contents API reports no such path at that commit; `github.commit_is_readable` corroborates it (the contents API returns the same 404 for "no such path" and "no such repository, as far as your credentials go"); and the cited path matches nothing in the diff's own file list, which `post_review` already computes as `commentable_lines(diff)` and now threads through to the guard. That last condition exists because **nothing upstream normalizes `finding.file`** — models drop a directory prefix (`app.py` for `src/pkg/app.py`), add one, or emit a leading slash that `quote(path, safe='/')` turns into a `contents//src/...` URL — so a mis-cited path on a live defect 404s identically to a hallucinated one, and suppressing it would drop a real finding over a typo *and* pre-empt the relocation (`diff_parser.find_best_file_for_finding`, `_place_finding_inline`) that already fixes that exact shape. With no file list supplied, or an empty one, nothing is suppressed for absence at all. **Fix-already-present** requires a code span from the finding's own `suggestion` to be found verbatim (whitespace-normalized) in the file. `suggestion` is **not** a remedy field by construction — `personas.py` types it as a free-form `"string or null"` — and models routinely quote the current code beside the fix, so naively mining every span inverts the guard: the offending code is present at head *because the fix was never applied*, and a live finding gets labelled stale. Three filters narrow the spans to something that can only be a remedy: when a suggestion carries several fenced blocks only the **last** is read (the before/after convention puts the remedy last, so a "Current: … / Change to: …" pair of fences no longer matches on the *current* half); any span that **also appears in `finding.message`** is discarded as the code being complained about rather than the fix for it; and a span must carry at least **four distinct word tokens** as well as clearing the length and code-punctuation floors, which rejects `httpx.get(url)` (14 characters, parenthesized, and the thing the finding is *about*) and bare filenames like `requirements.txt` (a lone `.` used to be enough) while still admitting the `import type { JSX } from "react";` shape this whole guard exists to catch. Nothing else qualifies — a cited line past end-of-file explicitly does not, since a misplaced citation is a relocation problem Vigil already solves and says nothing about whether the defect exists. The guard **fails open on every path** (network failure, 403, rate limit, missing token, unreadable blob, an exception from the guard itself, *and* an exception while rebuilding the verdicts — that mutation is inside the `try`, and computes every replacement list before assigning any of them, so "findings deleted from the review but never reported as suppressed" is not a reachable state). Both of its HTTP clients pass `follow_redirects=True`, because `httpx.Client()` defaults to `False` and `raise_for_status()` raises on a 3xx: without it, a single repository or owner rename would land every request in the `except` and silently switch the guard off for the whole review. It **never touches `ReviewResult.decision`**: a REQUEST_CHANGES that loses every one of its findings still posts as REQUEST_CHANGES, so the approve-only cleanup paths (#48 dismissal, #61 thread resolution) cannot be reached by suppressing findings. Withheld findings are logged and rendered in the review body under **Suppressed Findings** with their location, severity and reason — a guard that silently deleted findings from a merge gate would be indistinguishable from the bug it fixes. **(B)** `build_conversation_context` skipped Vigil's own output in the *reviews* loop but not the *comments* loop, and `post_review`'s final fallback posts the entire review body — findings text included — as an issue comment. Vigil therefore read its own prior CRITICAL findings back in as "PR Conversation" evidence on the next round, defended only by prose in the prompt. The same `VIGIL_SIGNATURE` skip now applies to both loops. **(C)** After a rebase, `compare/{base}...{head}` does **not** 404 for the orphaned last-reviewed SHA — it silently computes against the merge base, so `changed_files` becomes the whole PR rather than "changed since the last review" and the existing `except` never fires. The review diff was never affected (it is always the full base-to-head diff), but `changed_line_map` is the sole evidence for auto-resolving Vigil's own threads, so a force-push could resolve threads whose code nobody touched. A new `github.is_ancestor_commit()` reads the two fields that give a rebase away (`status`, `merge_base_commit.sha`); when history has diverged, `vigil review` and `vigil resolve-addressed` treat the round as a fresh review and resolve nothing, degrading to the previous behaviour on any error. Fixes F2iLLC/vigil#74.
- **Specialists that never ran no longer render as green verdicts** — `review_diff()` synthesizes an `APPROVE` `PersonaVerdict` on two paths that make **zero model calls**: when no file in the diff matches a specialist's `file_patterns` (the `"No relevant files for this specialist — auto-approve"` branch, with empty `checks`, `findings`, and `observations`), and when the specialist's model call fails transiently (`_is_transient_llm_error`, which does at least attach a `reviewer_unavailable` observation). Both then rendered in the posted review body as `| ✅ | **Security** \`VGL-xxxx\` | APPROVE |` — byte-identical to a specialist that read the diff and found it clean — were counted in the `N/N specialists approved` footer tally, and were reported to the **lead model** in its own prompt as `### Security [VGL-xxxx]: APPROVE`, so the final gate was misled by the same defect as the humans and bots reading the PR. The `*Reviewed commit X with Y*` header line printed unconditionally, asserting the commit had been reviewed with that model even when nothing had been asked of it. `PersonaVerdict` now carries `reviewed: bool = True` plus a machine-stable `skip_reason` (`no_files_in_scope`, `reviewer_unavailable`), set at both synthesis sites, and every rendering surface keys off it: a skipped specialist's row becomes `| ⏭️ | **Security** \`VGL-xxxx\` | NOT REVIEWED — no files in scope |`, with no check-mark and without the word `APPROVE` anywhere on it; the footer counts it separately (`1/2 specialists approved · 1 not reviewed`); the header degrades to naming the configured model *without* claiming it reviewed anything when no specialist ran at all; the lead is told the domain is `UNEXAMINED, not ... clean or approved` and must not count it as agreement with another specialist; and the body gains a stable `<!-- vigil-specialists-not-run: Security,Performance -->` marker, emitted only when at least one specialist was skipped, so downstream automation can detect a partial review without substring-matching prose — the same contract as the `<!-- vigil-did-not-run -->` marker `action.yml` posts when Vigil itself could not run. The console reports the same way, because it carried the same false statement in a blunter form: `vigil review`'s live per-specialist line printed a green `APPROVE Security \`VGL-xxxx\` - clean` for a skipped specialist — the `if not detail: detail = " clean"` fallback fires precisely *because* a synthesized verdict has zero findings and zero observations, so the one surface an operator watches while deciding whether to trust a run asserted a clean domain nobody had examined — and now prints `⏭️ NOT REVIEWED Security \`VGL-xxxx\` - no files in scope`, in yellow, with the reason occupying the slot `clean` used to; the closing `N/N specialists approved` tally is corrected to match the review body's. **This is reporting-only.** `decision` stays `"APPROVE"` on both paths, so `is_blocking_decision()`, `BLOCKING_DECISIONS`, the lead's aggregation, the submitted GitHub review event, and the inline-thread suppression from #52 are unchanged in effect; a dedicated "gating did not change" test guards that boundary, because a fix for a misleading report must not quietly become a merge-gating change. The single change to what a *model* sees is the lead's prompt. The non-transient error path is deliberately untouched — it already sets `decision="ERROR"` and renders as `⚠️ ERROR` with a `reviewer_error` finding, which nobody mistakes for a completed clean review. That fixes the marker's scope, which is stated on the constant so the next reader is not misled by it: `vigil-specialists-not-run` enumerates specialists that were **skipped** (`reviewed=False`) and deliberately does not list one whose model call failed non-transiently, so absence from the marker is *not* a claim that a specialist reached a verdict — automation asking "did every specialist actually conclude?" must check for the `ERROR` decision as well. Reported as F2iLLC/vigil#66 after a documentation-only auto-approve posted a formal GitHub approval showing six specialist reviewers each ✅ APPROVE (1/1 checks pass) for a code path that made zero model calls, and two automated readers cited that table as evidence a real review had happened. **That specific bypass was already deleted from `main` by #63** and is not reintroduced or re-fixed here; what this addresses is the surviving class of the same defect, which #66 states in one line — *a verdict table implies verdicts were reached*. Same policy as item 1 of #51 ("fail loudly") and #53: Vigil must never render green for review work that did not happen. Fixes F2iLLC/vigil#66.
- **An accepted approval now resolves Vigil's own open review threads** — Nothing anywhere resolved a Vigil review thread because the review *concluded* `APPROVE`. The only resolver on the review path, `resolve_addressed_threads`, is diff-driven: it resolves a thread only when the thread's file appears in `changed_files`, the incremental diff since the last review. Combined with cross-round dedup that made the leak permanent rather than transient — round 1 opens a thread on `foo.py`; round 2 touches only `bar.py` and concludes `APPROVE`; `foo.py` is absent from `changed_files` so the thread is not resolved, and dedup suppresses re-posting the finding, so nothing ever re-touches the thread. The PR is left carrying an unresolved Vigil thread underneath an approving Vigil review, indefinitely — under a "resolve all threads before merge" ruleset, a merge blocker attached to a review that approved the PR. A new decision-driven resolver, `resolve_vigil_threads_on_approval()`, is called from the same `cli.py` branch as `dismiss_stale_vigil_blocks` and inherits its three guards: the review must have posted without raising, this run's verdict must be `APPROVE`, and GitHub must have accepted it as `event=APPROVE` — **not** a degraded `COMMENT` or an issue-comment fallback, since clearing the visible findings while the PR remains blocked is strictly worse than the bug being fixed. `REQUEST_CHANGES` and `BLOCK` deliberately change nothing. The call is wrapped so cleanup can never fail a review that has already posted. Scope is **all** of Vigil's still-open threads on the PR, deliberately not just the current run's: `session_id` is per-*specialist-run*, not per-review-round (`PersonaVerdict.session_id`), so the stranded threads this exists to clear necessarily carry different session IDs, and a current-session-only implementation would resolve nothing in exactly the reported scenario. Vigil's own threads are identified by the `VGL-` marker in the thread body (`VIGIL_SESSION_PATTERN`), the same gate the rest of the module uses; human-authored threads are never touched. Fixes F2iLLC/vigil#61.
- **Documentation PRs are reviewed instead of auto-approved** — `review_diff()` short-circuited the entire review when `is_documentation_only()` matched the diff: it synthesized an `APPROVE` `PersonaVerdict` for every specialist with `checks={"documentation_only": "PASS"}`, fired `on_specialist_done` for each, made **zero model calls**, and returned an approving `ReviewResult`. That is a real approving review posted to the PR, and it satisfies branch protection — Vigil reported success having reviewed nothing. The predicate driving it was far broader than "documentation": `is_documentation_path()` OR'd a **basename-only** match against `*.md`, `*.mdx`, `*.rst`, and `*.txt` with **no path constraint at all**, so any Markdown or text file anywhere in the tree qualified. Markdown is the substrate for governance policy, security procedure, runbooks, ADRs, project plans, and confidentiality boundaries — none low-risk by virtue of a file suffix. Field failure: F2iLLC/LunaOS#4175 changed two `.md` files under `ai/admin/personal/` committing confidential legal material (named counsel, per-firm decline reasons, standing exclusions, contact routes) in violation of that project's own confidentiality boundary, and Vigil returned APPROVE with all six specialists green on `documentation_only: PASS`; a different reviewer caught it. Two changes, per the owner ruling of 2026-08-11. **(A)** The short-circuit is deleted — documentation diffs now go down the normal specialist and lead path like any other diff, including external-context resolution. **(C)** `is_documentation_path()` is narrowed so it stops overclaiming regardless: classification is by *path*, not extension. A file is documentation only when it is under `docs/`, `documentation/`, `.github/ISSUE_TEMPLATE/`, or a PR-template path, or is a repository-root convention file (`README*`, `CHANGELOG*`, `CONTRIBUTING*`, `CODE_OF_CONDUCT*`, `LICENSE*`, `NOTICE*`) **at the root itself** — `DOC_FILE_GLOBS` is replaced by `ROOT_DOC_FILE_GLOBS` and the bare extension globs are gone. `ai/admin/personal/counsel.md`, `src/some/deep/path/notes.md`, and `packages/core/README.md` are no longer documentation; `docs/setup/install.md` and a root `README.md` still are. `is_documentation_path()` and `is_documentation_only()` are kept as a tested, reusable classifier with **no production caller** and carry an explicit note that neither is a review-skipping gate and must not be reintroduced as one without an owner ruling. Same class as #53, which made a *skipped* Vigil fail loudly rather than render green; here Vigil ran, reported success, and did nothing. Fixes F2iLLC/vigil#62.
- **Inline comments only on a blocking verdict** — GitHub renders every inline review comment as an *unresolved review thread*, so under a ruleset that requires all threads resolved, a Vigil review that approved while posting inline comments blocked the pull request it had just approved. `post_review` consulted `result.decision` only to pick the review event; every specialist and lead finding went inline regardless. Inline placement is now reserved for `REQUEST_CHANGES` and `BLOCK`. Any other verdict — `APPROVE`, or a decision that maps to a bare `COMMENT` — posts zero inline comments and reports its findings in the review body under **Advisory Findings**, labeled non-blocking and carrying their original file and line, so nothing the review found is dropped. The suppression holds on every rung of the 422 fallback ladder, including the `COMMENT` retries and the final issue-comment fallback. Observations were already summary-only and are unchanged, as is the verdict logic itself. Threads opened by *earlier* rounds were left for `vigil dismiss-resolved` or `vigil resolve-addressed` to clear; that gap is what F2iLLC/vigil#61 (above) closes — an accepted approval now resolves them directly. Fixes F2iLLC/vigil#52.
- **`find_best_file_for_finding` fallback** — Now correctly skips files with empty line sets when falling back to the first alphabetical file.
- **`_mock_response` helper** — Fixed falsy `{}` bug where `json_data or []` treated empty dict as falsy.
- **`Detect Python` guard now probes `venv`, not just version** — The guard previously checked only that system `python3` was >= 3.10 before skipping `actions/setup-python`. On Debian/Ubuntu, a 3.10+ interpreter can still lack `ensurepip` (the `python3.X-venv` package is separate), so `python3 -m venv` failed downstream even though the guard reported success — and `actions/setup-python` was skipped exactly when it was needed. Now runs `python3 -m venv` against a throwaway directory as part of the check and falls back to `actions/setup-python` if it fails. Root cause of F2iLLC/LunaOS#3775 (fleet-wide: also hit bioqms-core, relara, praxislms via the same `lunaos-light-1` runner).
